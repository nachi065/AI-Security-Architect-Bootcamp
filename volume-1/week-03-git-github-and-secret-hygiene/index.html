    Week 3: Git, GitHub and secret hygiene¶

    Volume 1 · Part 1 (Weeks 1-3): Systems, networking, Linux and secure Git

    Part goal

    understand how an LLM-powered application is deployed and where its trust boundaries are, and set up the lab and portfolio that the rest of the programme depends on.

    You will be able to: work in branches and pull requests, sign your commits, and stop secrets from reaching a repository.

    Scan twice: locally before the commit and again in CI. If a secret slips through, rotate it first.

    Core concepts

    • Git model. Working tree, staging area, local repository, remote. Commits are snapshots linked in a history; branches are movable pointers.
    • Daily commands. git init, clone, add, commit, status, log, diff, branch, switch, merge, rebase, pull, push, stash.
    • Pull requests. The unit of review. Small PRs with a clear description get better review.
    • Signed commits. A signature shows a commit came from a key you control. Git can sign with an SSH key (see Git and GitHub documentation for current setup).
    • Secrets hygiene. A secret in history stays there even after deletion. Prevent with .gitignore, pre-commit hooks and secret scanners (for example gitleaks); if one leaks, rotate it first, then clean up.
    • CI basics. GitHub Actions runs checks on every push or PR. Dependency alerts (Dependabot) flag vulnerable libraries.

    Study plan (about 9 hours)

    1. GitHub Skills interactive courses and the Git official documentation (Pro Git book chapters on basics and branching), about 4 hours.
    2. Read the documentation of your chosen secret scanner and of the pre-commit framework, about 1 hour.
    3. Lab, deliverable and Checkpoint A, about 4 hours.

    Guided lab: the portfolio repository with a secret-catching CI check

    1. Create the repository ai-security-bootcamp with folders week01 to week03, notes/ and labs/. Move your Week 1-2 deliverables in.
    2. Work on a branch, open a pull request to your own main, review it, and merge.
    3. Configure commit signing and confirm GitHub shows the commits as verified.
    4. Add a pre-commit hook that runs a secret scanner locally.
    5. Add a CI workflow that runs the same scanner. Follow the scanner's current official setup instructions rather than copying a workflow from memory.
    6. Prove it works: on a throwaway branch, add a file containing an obviously fake test secret (for example the AWS documentation example key AKIAIOSFODNN7EXAMPLE). The check must fail. Never commit a real credential, even to test.
    7. Delete the throwaway branch.

    Deliverable and gate

    • The ai-security-bootcamp repository with working CI.
    • Checkpoint A. Combine the Week 1-3 self-check questions into a 20-question closed-book quiz. Pass mark is 80% (16 of 20). If you score lower, repeat the weak weeks' labs before moving on.

    Self-check

    1. What is the difference between git merge and git rebase?
    2. You committed an API key and pushed. What do you do, in order?
    3. Why does deleting a secret in a new commit not fix the leak?
    4. What does a signed commit prove?
    5. What does your CI check catch, and what can it miss?
